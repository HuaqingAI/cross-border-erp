# Epic 8 Context: 数据导入与系统配置

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Epic 8 解决系统上线与后续主数据治理的两类基础能力：一是让管理员能够批量迁移历史分类、SPU、SKU 数据，并在导入过程中得到可反复修正的校验反馈；二是把全局枚举配置集中化，并逐步让各业务模块改用统一枚举契约，减少硬编码与字段口径漂移。对开发而言，这个 Epic 的核心价值是把“批量初始化数据”和“全局字典治理”沉淀为可持续复用的底层能力，而不是一次性页面功能。

## Stories

- Story 8.1: Excel 导入模板与批量导入 API
- Story 8.2: 数据导入前端页面
- Story 8.3: 枚举值配置管理
- Story 8.4: 价格与资料模块枚举接入
- Story 8.5: 证书、FAQ 与 SPU 模块枚举接入
- Story 8.6: SKU 模块枚举接入与契约收口

## Requirements & Constraints

- 数据导入必须覆盖三类对象：分类、SPU、SKU，且支持模板下载、上传校验、失败修正后重复上传、确认后正式导入。
- 导入校验至少包含格式校验、必填项校验、唯一性校验和关联有效性校验；结果需要能区分成功条数、失败条数和逐行失败原因。
- 导入能力是系统上线迁移工具，目标数据规模包括约 8000 条历史 SKU，因此首版就要考虑分批导入、重复修正与可追踪反馈，而不是一次性脚本。
- 数据导入的权限口径以管理员为核心；PRD 的权限矩阵同时允许产品部操作导入，开发时需要结合现有权限实现明确最终策略，避免前后端口径不一致。
- 导入 1000 条数据时处理时间目标为 30 秒以内；超过时需要有进度反馈，因此实现上不能只考虑同步阻塞式黑盒导入。
- Epic 8 的后半段依赖统一枚举中心，国家/地区、单位、产品类型、包装类型等字段最终都要收口到稳定编码或枚举键，导入设计不要固化会阻碍后续枚举收口的自由文本契约。

## Technical Decisions

- 架构将数据导入映射到后端 `app/*/import_tasks.*`，并预期使用 `import_service`、批量写入和进度状态表来支撑 FR28-31。
- Excel 导入属于明确的非功能约束点，建议从一开始就预留异步处理、流式解析或任务状态跟踪能力，而不是把所有状态只存在一次请求生命周期里。
- 后端现有主数据模块已经拆分为分类、SPU、SKU 等独立 service/router/schema，8.1 应复用这些领域模型与校验约束，而不是绕开现有 service 直接写库。
- API 响应需要继续遵守项目统一错误返回与权限机制；导入失败明细应设计成前端可直接消费的结构，为 8.2 页面表格展示预留稳定契约。
- 现有系统大量字段已经存在继承、唯一索引、子表结构与字段级权限，SKU 导入尤其涉及基础信息、产品属性、包装信息、报关信息，模板与写入策略需要明确哪些字段首版必须支持、哪些必须走现有派生逻辑。
- 若导入过程需要暂存校验结果再确认导入，必须选择一个明确的中间态载体，并定义过期、幂等与重复确认边界。

## UX & Interaction Patterns

- 管理员是该 Epic 的关键使用角色，关注点是批量操作反馈和系统配置可控感，因此导入相关 API 设计需要天然支持“可解释结果”而不是只有成功/失败布尔值。
- 数据导入的目标用户旅程是：下载模板、整理数据、上传校验、查看失败明细、修正后重传、确认导入完成；这要求后端返回值能支撑逐步修正，而不是只适合一次性调用。
- 当导入耗时较长时，需要能让前端展示进度条或百分比，这意味着后端至少要提供可轮询或可查询的进度状态。

## Cross-Story Dependencies

- 8.2 完全依赖 8.1 提供的模板下载、上传校验、确认导入与进度查询能力。
- 8.3-8.6 逐步把业务字段收口到统一枚举中心，因此 8.1 在设计导入字段时要避免与后续枚举编码策略冲突。
- 分类、SPU、SKU 的导入都依赖已有主数据模型与唯一性约束；其中 SKU 导入还依赖前序 Epic 已完成的分类/SPU/SKU 基础能力。
